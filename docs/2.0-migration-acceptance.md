# Auton 2.0 migration acceptance

Engineering checkpoint: 19 November 2026. The published candidate is
**2.0.0rc6**, from `f39c95b4236d902dbbaf9517e0881a770bc6a42e`.
The stable target date is not an automatic approval to publish or upgrade.

## Reproducible installed-package migration

`.github/scripts/check-2.0-migration.py` uses separate installed **1.5.3** and
**2.0** environments and runs their daemons on loopback, outside the source import path. It creates
synthetic accounts and harmless jobs, stops the original daemon, and tests copies
of its configuration, authentication database and SQLite job history.

The check covers:

- existing bearer tokens and completed outputs after migration;
- required authentication when `auth_mode` is omitted in 2.0;
- rejection of implicit client arguments/environment before admission;
- fixed server arguments and environment files;
- six terminal YAML imports and explicit argument/environment permissions;
- selected environment files, forbidden uploads and invalid values;
- HTTP 400, 403, 409 and 429 contracts;
- distinct outputs for two principals using the same public job ID;
- per-principal capacity without blocking another principal;
- restart, maintenance refusal and rejection of nested terminal imports;
- unchanged original backup hashes and rollback using the **original** databases.

The installed-release gate calls this check for the 2.0 series before image,
package or GitHub release publication. It creates its own pinned 1.5.3 environment
and uses the candidate wheels built by that run. The existing Python matrix,
Redis, Docker, Compose, browser and documentation jobs remain required.

To reproduce with two disposable, already installed environments:

```sh
candidate/bin/python .github/scripts/check-2.0-migration.py \
  --previous-python previous/bin/python \
  --candidate-python candidate/bin/python
```

The previous environment must contain `auton==1.5.3` and `autond[auth]==1.5.3`.
The candidate environment must contain both matching 2.0 packages with the
daemon authentication extra. The script never accepts production paths, runs
production commands or emits tokens. Its summary explicitly labels the scope
as synthetic engineering acceptance. The fixture data is removed on completion.

## Recorded local evidence

- Published PyPI packages `auton` and `autond`, both `2.0.0rc6`, passed the
  isolated 1.5.3 migration above on Python 3.12.14, with HTTPdis 0.7.1 and
  Sonicprobe 0.3.65.
- The source suite collected and executed 288 cases: 284 passed and four were
  deliberately skipped (three require real Redis; one requires root-to-service
  user transition). Those prerequisites belong to the existing CI jobs.
- CI helper suite: 18 collected/executed, 17 passed; the generic pytest-runner
  case was skipped without pytest. Auton's runner remains unittest.
- Client and daemon wheels/source distributions passed strict Twine and
  distribution identity/install checks. Documentation built with Sphinx `-W`.
- The installed-release check passed entry-point/assets checks and real CLI
  compatibility in both directions with 0.3.2, plus the 1.5.3 migration above.
- The unmodified RC6 source had passed the [Tests workflow](https://github.com/decryptus/auton/actions/runs/42357810390)
  and [publication workflow](https://github.com/decryptus/auton/actions/runs/42357810456).
  These historical runs do not validate later changes; the current PR's checks
  remain required.

This is not a sustained-load test, an acceptance of every authentication provider,
or an operator report from a deployed installation. It does not replace the
existing Redis and browser/OIDC coverage.

## Existing-installation outcome — 19 November 2026

The operator migration check passed on an isolated copy of a retained deployed
**1.3.1** installation, using the published **2.0.0rc6** packages. The source
installation was stopped before this work. It used required authentication,
SQLite accounts and job history, an endpoint user allowlist, and implicit client
arguments. The check did not upgrade or reactivate the original installation.

- One historical completed job remained readable with its original output.
  A harmless baseline job was added on the copy; both results survived RC6 and
  restart. A separate pre-upgrade copy also passed using the installed 1.3.1 image.
- The original bearer token was already rejected by 1.3.1. A fresh token was
  issued **only in the copied account database**, then accepted by RC6 and the
  rollback copy. This does not establish continued validity of the original token.
- The published 1.5.3 offline checker identified four implicit input categories.
  RC6 rejected implicit arguments before admission. An explicit zero-value
  argument rule permitted the required flag; unknown/repeated arguments and
  extra values, client environment, uploaded files and selected envfiles returned
  HTTP 400 without creating jobs. Unauthenticated requests returned HTTP 401.
- A second disposable account on the copy received separate results for the
  same public job ID. Duplicate submission returned 409; the active-job quota
  returned 429 without blocking the other principal. Isolation survived restart.
- Original configuration, credentials and state files were unchanged, as were
  existing container identities, start times and restart counts. No existing
  service was restarted. Test containers had no external network or published ports.

The target command was replaced on the copy with a harmless argument reporter.
Test-only retention was extended to inspect the old completed result without
rewriting timestamps or replaying it. Imports, envfile selection and uploads were
not used by this source configuration; their broader coverage remains synthetic.
This check does not certify end-to-end integrations, every authentication provider,
an active-service cutover, sustained load or long-duration stability.

Six collected/executed boundary checks and real disposable baseline/candidate/
rollback qualification passed before accessing the retained installation.
Detailed deployment evidence remains private; [issue #55](https://github.com/decryptus/auton/issues/55)
records the sanitized outcome. No release-blocking regression was found in this scope.
